# 抖音账号持续监控 Skill

## 职责边界（重要）

| 需求 | 用哪个技能 |
|---|---|
| **周期性监控账号**（新作品/涨粉/数据曲线） | **本技能** |
| 一次性深度分析某个账号的评论区话题 | `douyin-comment-analyzer` |
| 实时监控直播间弹幕 | `douyin-live-monitor` |

本技能和 `douyin-comment-analyzer` 共用 Chrome 登录态 profile
（`~/.workbuddy/douyin_chrome_profile`），扫码一次两边都能用。

### 三套监控名单的边界与互斥（2026-09-18 确立）

抖音链路共有三套账号名单，由三个定时任务分别维护，**职责不同、不可混用**：

| 名单 | 载体 | 谁在写 | 谁在读 | 职责 |
|---|---|---|---|---|
| 巡查名单 | `data/monitor.db` → `accounts` 表 | 手动 `add` / `discover_services.py` | 04:00 巡查 | 粉丝与作品数快照、新作品发现、爆款倍数判断 |
| 评论名单·个人 | `~/.workbuddy/douyin_analysis/_archive/s_watchlist.json` | 手动维护 | 09:00 任务 | S 级出海服务博主的评论区需求信号 |
| 评论名单·园区 | `~/.workbuddy/douyin_analysis/_archive/parks_watchlist.json` | `reconcile_projects.py` / 反向补搜 | 13:00 任务 | 园区官方/招商号的入驻意向信号 |

**互斥规则（必须遵守）：**

1. **`s_watchlist.json` 与 `parks_watchlist.json` 必须互斥** —— 同一 `sec_uid` 不得同时出现在两处。
   两者的评论采集由不同任务、在不同时间执行，重复会导致同一账号评论被抓两遍，
   且写入同一个 `account_<昵称>` 目录互相覆盖。若冲突，保留在 `parks_watchlist.json`。
   定期自检：
   ```bash
   /Users/goterra/.workbuddy/binaries/python/envs/default/bin/python3 - <<'EOF'
   import json, pathlib
   P = pathlib.Path.home()/'.workbuddy/douyin_analysis/_archive'
   s = {a['sec_uid'] for a in json.load(open(P/'s_watchlist.json'))['accounts']}
   p = {a['sec_uid'] for a in json.load(open(P/'parks_watchlist.json'))['accounts']}
   print('冲突账号:', s & p or '无')
   EOF
   ```
2. **`monitor.db` 与两份评论名单允许重叠**（2026-09-18 实测：与 parks 重叠 6 个、与 s 重叠 5 个）。
   这是有意设计——巡查看「量」（粉丝/作品数/爆款倍数），评论任务看「质」（评论区需求信号），
   两者数据落点不同（db 表 vs 文件目录），不构成重复采集。**不要为了「去重」把账号从某一侧删掉。**
3. **评论抓取职责只有一个出口**：04:00 巡查**不得**抓评论正文，必须带 `--no-comments`。
   原因：巡查抓到的评论只写进 `monitor.db` 的 `comments` 表，而该表**没有任何下游脚本消费**
   （全仓搜不到 `SELECT ... FROM comments`），属于只写不读的死数据。省掉每个新作品 60 次
   滚动（约 12-20 秒/条）可显著缩短巡查时长。评论内容分析统一由 09:00 / 13:00 两个任务负责。
   确需单条作品的评论时，用 `monitor.py detail <aweme_id>` 手动补抓。

### 定时任务序列与登录态主责（2026-09-18 两次调整）

抖音链路原有 4 个自动化任务，因「13:00 商贸城发现」与「20:00 出海服务拓号」同为搜索抖音
用户 tab 发现账号、且各自产出一份当日清单快照互相打架，已合并为 1 个任务。现为 3 个：

| 时间 | 任务 | 职责 |
|---|---|---|
| 04:00 | 抖音账号监控巡查 | 到期账号快照 + 新作品 + 爆款倍数（`--no-comments`） |
| 09:00 | 抖音出海非洲每日监控（关键词+S级账号）+归档 | 评论采集 + 需求密度 |
| 13:00 | 抖音账号发现（商贸城项目库 + 出海服务拓号） | 拓号入库 + 当日清单快照 + 园区项目库核验 |

**登录态主责在 04:00（2026-09-18 从 09:00 前移）**：只有 04:00 任务负责检测登录态失效并
提示用户扫码续期；09:00 与 13:00 遇到失效只记录并跳过，不弹扫码、不提示续期——
避免三个任务各自弹窗互相踢登录态，也避免用户收到三条重复提醒。

**为什么前移到 04:00**：04:00 是当天第一个使用浏览器的任务。检查点越靠前，用户越早收到提醒、
能救回的任务越多 —— 04:00 报失效，用户在早上看到后可在 09:00 前扫码续期，同时救回 09:00 与
13:00 两个任务；若检查点仍在 09:00，用户 09:45 才得知，09:00 任务已经失败，只能救 13:00。
登录态有效期约 2-7 天，三个任务共用同一个 `~/.workbuddy/douyin_chrome_profile`。

**各任务实测耗时**（2026-09-18 从 `~/.workbuddy/logs/automation.log` 读取，日志为 UTC，下表已换算为北京时间）：

| 任务 | 起止 | 耗时 |
|---|---|---|
| 04:00 巡查（含评论抓取，旧行为） | 04:00 → 04:42 | 42 分钟 |
| 04:00 巡查（`--no-comments`，预估） | — | 12-18 分钟 |
| 09:00 监控 | 09:07 → 09:50 | 43 分钟 |
| 13:00 发现 | 13:00 → 13:42 | 42 分钟 |

`--no-comments` 是 04:00 任务最大的单项优化：原先每个新作品要滚动 60 次抓评论，
而抓到的评论只写进 `monitor.db` 的 `comments` 表，该表**没有任何下游脚本消费**（属只写不读的死数据）。

### 添加账号到监控名单

```bash
# 直接丢分享口令/短链/主页链接/视频链接，都能识别
python3 monitor.py add "8.94 复制打开抖音，看看【xxx的作品】 https://v.douyin.com/xxxxx/"
```

首次添加会自动：解析 sec_uid → 打开主页 → 抓账号信息 → **把当前视频全部录为基线**（基线不报警）。

### 周期性巡查

```bash
python3 monitor.py run               # 巡查「本轮到期」的账号（按分层，见下节）
python3 monitor.py run --no-comments # 只抓数据，不抓评论（快很多，定时任务用这个）
python3 monitor.py run --all         # 强制全量（人工排查/首次建库/怀疑漏报时才用）
python3 monitor.py run <sec_uid>     # 只巡查指定账号（忽略分层，强制巡）
```

输出每次巡查的粉丝/获赞/作品数、粉丝变化量、新作品列表。
**新作品被确认后，会自动打开视频页抓单条数据 + 评论区**，存进库。
有变化时额外写 `data/changes_<时间戳>.json`。

单次巡查最多处理 20 条新作品（`MAX_DETAIL_FETCH`），超出部分下轮继续，防止任务失控。

### 巡查分层与自适应降频（2026-09-18 新增）

账号池从 13 个涨到 81 个后，每天全量巡一遍的成本持续上升。分层让「没动静的账号」少巡几次，
而**不减少任何发现能力** —— 因为判定依据就是「它有没有发新作品」。

| 层 | 周期 | 判定条件 |
|---|---|---|
| **S** | 每天 | 近 7 天作品数有增长；或加入未满 7 天（观察期新号）；或人工重点名单成员 |
| **A** | 3 天一轮 | 作品数停顿 7~21 天 |
| **B** | 7 天一轮 | 作品数停顿 21 天以上 |

```bash
python3 monitor.py tier                  # 查看分层分布与各层名单
python3 monitor.py tier --auto           # 按作品数停顿天数重算（预演，不写入）
python3 monitor.py tier --auto --apply    # 确认后写入，并自动错峰排期
python3 monitor.py tier <sec_uid> S|A|B  # 手动指定单个账号
```

`--auto` 默认**预演不写入**（分层会改变系统行为，先看结果再启用）。
手动 `tier <sec_uid> S|A|B` 会**同步改写排期**：升到 S 清空 `next_check`（立即到期，下次运行就巡），
降到 A/B 则从今天起算一个周期。不同步的话会出现「手动设为 S、却因残留排期还得等 3 天才巡」
——命令说 A、排期说 B，行为与意图相反。

**为什么用「作品数是否增长」判定，而不是粉丝/签名/发布时间**（三个候选都被实测否掉）：

| 候选依据 | 实测结果 | 结论 |
|---|---|---|
| 签名里的服务词 | 81 个里 62 个命中强服务词——因为库本来就是拓号引擎按服务词灌进来的 | 无法区分，等于没分层 |
| 粉丝量 | 1540 粉的科特迪瓦清关号与 250 万粉的博主对业务同等重要 | 与业务价值不相关 |
| 作品发布时间 `publish_time` | 40/81 为 NULL（只在抓过评论详情页的作品上才有） | 覆盖不足 |
| **作品数 `aweme_count` 是否增长** | 每天巡查必采的主页硬字段，不受详情页抓取影响 | ✅ 采用 |

**三条必须守住的设计约束**（每条都对应一个已踩/已避的坑）：

1. **重点号保护**：`s_watchlist.json`（09:00 任务的 S 级出海服务名单）成员强制留在 S 层，
   不参与自动降频。理由：自动判定只看「有没有发新作品」，而物流/清关/园区服务号往往低频发帖、
   评论区却持续聚集需求 —— 这类号不能因为安静就被降频，那正是最该盯的对象。
2. **独立调度字段 `next_check`，不复用 `last_check`**。两个原因：
   ① 到期判定若用「`last_check` 距今 ≥ cycle 天」，会遇到 `last_check` 实测为 04:01:39、
   次日 04:00 运行时时间差只有 0.999 天的问题，`>= 1` 判 false，**全部 S 级账号被静默跳过**
   （任务显示成功、实际一个都没巡）；
   ② 错峰排期需要改写"下次巡查日"，而 `last_check` 会展示在清单里，被改写会让「上次巡查」变成假数据。
3. **必须错峰**：`--auto --apply` 会把降级账号依次排入未来第 1..cycle 天。
   不做错峰的话，同批降级的 23 个账号会在 3 天后**同一天集体到期**，那天照旧 81 个，白降一轮。
   实测错峰后稳态负载 65-66 个/天，波形平稳无尖峰（全量 81 个）。

**降频是自愈的**：账号一发新作品，下轮巡查（≤cycle 天）即发现，作品数增长 → 自动升回 S。
不需要任何人工干预。巡查失败的账号不会更新 `next_check`，因此下轮仍会到期重试。

**实测收益（2026-09-18，全员 81 个）**：S=58 / A=23 / B=0，日均巡查 65.7 个，降幅 19%。
降幅偏小的原因是 57 个账号加入未满 7 天、仍在观察期；随着账号池沉淀，降幅会自然扩大。

python3 monitor.py list              # 监控名单 + 最新数据

`videos` 命令是看「哪条爆了」的主出口。它会算出该账号点赞数的**中位数作为常态基线**，

新增账号后务必先跑一次 `backfill` 建立基线，否则前几条新作品无法判断是否起量。

## 已知坑（务必遵守）

> 2026-09-18 新增的「巡查分层」自带 3 个独立的坑（时间差判定导致全员漏巡、同层账号集体同日到期、重点号被静默降频），已集中在
> 「巡查分层与自适应降频」一节说明。**改动选号逻辑或 `tier` 命令前必读那一节。**

1. **新作品误报（本技能最大的坑，务必理解后再改代码）**

   有两层原因，需要两道防线：

   - **表层：主页异步加载抖动。** 每次打开主页，滚动加载出的视频集合并不完全一致。
     只按「视频 ID 没见过」判定，会把「上次没加载到的老视频」误报成新作品（实测相隔 1 分钟误报 8 条）。
     → 防线一**二次确认**：新 ID 首次出现只记 `seen_count=1` 不报警，连续第 2 次巡查仍出现才判定为真新作品。

   - **深层：基线永远不完整。** 主页一次只能加载几十条，而账号可能有几千个作品
     （实测「非洲达哥」3680 个作品只能看到约 30 条）。所以只要滚动深度一变，
     就会持续涌出「基线里没有的老视频」。13 个账号首轮巡查后，待确认队列直接堆到 **112 条**，
     二次确认对此完全无效（它们会连续两次都出现）。
     → 防线二**作品总数硬约束**：`expected_new = 当前 aweme_count - 上次 aweme_count`。
     **作品总数没增加，就绝不可能有新作品**，本次见到的所有新 ID 一律直接标为基线。
     这是最有效的过滤器，不要移除。

   - 防线三**基线轮不报警**：`accounts.baselined=0` 时（首次巡查）只建基线不报警。

   ⚠️ **两处反直觉的实现约束（踩过，都是真 bug，别改回去）**

   - **「作品总数硬约束」只在插入待确认队列时用一次，不要在确认放行时再用一次。**
     账号发完一条就停更时，下一轮 `expected_new=0`，若确认条件也要求 `expected_new>0`，
     那条真新作品会**永久卡在 `notified=0`**（实测非洲蔡 2026-09-02 那条被卡死一整轮）。
     正确写法：确认放行只看 `seen_count>=2 and not notified and baselined`，
     队列规模已被插入时的配额限死，不需要再卡一道。
   - **基线 INSERT 必须显式写 `notified=1`。** 表默认是 0。
     `cmd_add` / `cmd_detail` 只写 `seen_count=2` 不写 `notified` 的话，
     这些老视频会在该账号作品数首次增长时被当成新作品报出来
     （实测新增账号「非洲于哥」带进来 24 条这样的脏行）。
     `cmd_import_existing` 一直是对的，照它写。

   📌 **给调用方（含自动化）的提醒：stdout 的条数完全不可信，必须查库。**
   - 打印「无新作品」≠ 真没新作品：只表示本轮没走到报警，新 ID 可能还在二次确认队列里。
   - 打印「🆕 新增 N 个作品」的 **N 也不可信**：它只统计本轮走到报警的条目，
     而真新作品首轮进了队列（`seen_count=1`）根本不会打印。
     实测 2026-09-04 那轮 stdout 只报 5 条（且全是上轮遗留），
     查库才发现另有 10 条真新作品。
   - **正确做法**：跑完后查
     `SELECT ... FROM videos WHERE notified=0`（拿待报全量），
     再叠 `discovered_at >= 本轮开始时间 AND title IS NOT NULL` 过滤掉基线补录的脏行
     （基线行没有 title）。两个条件结合才是本轮真新作品。

2. **作品点赞数可以直接从主页卡片批量拿，不必逐个打开视频页**
   主页每个作品是一个 `<li>`，内部文本节点顺序固定：
   `[可选「置顶」] → 点赞数 → 文案 → 文案(重复一次)`
   且 `<a href="/video/<id>">` 与 `<img alt="作者名：文案">` 在同一个 li 内，
   三者可在 li 级别精确关联。
   **收益**：13 个账号补完全部作品数据只要 6-8 分钟；若逐个打开视频页需 1 小时以上。
   所以 `backfill` 用主页方式，只有「新作品」才值得开视频页抓详情（要拿评论和转发）。

3. **主页数据同步必须放在新作品判定之后，且不能新增记录**
   `sync_homepage_videos(..., insert_new=False)`：若在判新之前同步，或允许新增，
   真新作品会被标成「已确认基线」而**永远漏报**。这是本技能最容易踩坏的一处，改代码时留意。
   只有 `backfill`（首次补数据）才用 `insert_new=True`。

4. **单条视频数据是 DOM 里的裸数字，必须以「举报」为锚点定位**
   视频页的点赞/评论/收藏/转发**没有标签**，就是几个连续的数字行，
   固定顺序 点赞 → 评论 → 收藏 → 转发，紧邻「举报」之前。
   RENDER_DATA 里**没有** `statistics` / `digg_count` 字段（实测为空，别浪费时间找）。
   更坑的是：页面上方播放器控件区会**重复出现同一组数字**，所以不能全文搜数字，
   必须从「举报」往前取，否则取到的是控件区那份。
   「发布时间」在「举报」之后 1-3 行，视频文案在这组数字之前。

   ⚠️ **两个变体（都踩过，别改回「固定 4 个数字」的写法）**

   - **转发数经常不渲染，只剩 3 个数字。** 实测狮王 2026-09-02 酒吧那条，
     「举报」往前只有 `96 / 14 / 3`（点赞/评论/收藏），转发位是个**纯标签行「分享」**。
     原来的写法要求凑满 4 个数才赋值，凑不满就整体放弃 → 点赞数变 `NULL`。
   - **数字之间会夹纯标签行（「分享」等）。** 收集时必须跳过这些标签，
     不能一遇到非数字就 `break`，否则标签会打断收集。
     → 现在的实现：往前收集最多 4 个数字、跳过 `分享/转发/收藏/评论/点赞/不喜欢/展开` 标签，
       收满 4 个 = 转发/收藏/评论/点赞，**只收到 3 个 = 收藏/评论/点赞**（转发留空）。

5. **统计字段在 DOM 文本，不在 RENDER_DATA**
   RENDER_DATA 里的 nickname 可能是页面其他作者。昵称优先取 `<title>`，
   粉丝/获赞从 body 文本抓取，且标签与数值**可能同行（"粉丝21.0万"）也可能分行**，
   需双路匹配。
   抖音号/IP属地/年龄/地区挤在同一行：`抖音号：123IP属地：科特迪瓦39岁香港`，需一次正则拆四项。

6. **评论抓取依赖 douyin-comment-analyzer 的 common.py**
   `monitor.py` 通过路径 import 它的 `extract_comments_from_page`（噪音过滤词表保持一份，
   避免两边漂移）。若该技能被删除或改名，脚本会降级到内置精简过滤器，
   评论噪音会明显变多。改这两个技能时要留意这条依赖。

7. **必须复用登录态 profile**
   用 `~/.workbuddy/douyin_chrome_profile`。无头模式易被识别，默认有头
   （`--start-minimized` 最小化，不打扰）。

8. **登录态会过期**
   长时间未用会掉线，脚本会提示扫码并等待最多 6 分钟。这是本方案唯一硬伤，需人工介入。

9. **巡查频率不要过高**
   每次巡查要开一次浏览器（单账号约 40-60 秒，抓评论的账号更久）。
   高频轮询无意义且加速风控，每天 1 次足够。

10. **详情写入必须用 COALESCE 保护，不能用 None 覆盖已知值**
   `extract_video_detail` 遇到风控/渲染失败时会返回 `None` 字段。
   若直接 `UPDATE ... SET digg_count=?`，会把主页同步来的已知点赞数**抹成 NULL**，
   导致该条永远算不出「相对常态的倍数」
   （实测狮王 2026-09-02 酒吧那条连续两轮被打空，只能手工还原）。
   → 所有详情写入统一用 `digg_count=COALESCE(?, digg_count)`，
   文本字段用 `COALESCE(NULLIF(?,''), title)`。`cmd_run` 与 `cmd_detail` 两处都得这么写。

11. **首轮基线账号必须禁止入待报队列（2026-09-05 修）**
   `cmd_run` 判新的三重约束里，`baselined` 原本只卡「确认放行」，没卡「插入队列」。
   结果只要 `expected_new` 被算大，首轮基线的老视频就会整批进 `notified=0` 队列。
   实测：拓号引擎写的快照 `aweme_count=0` → `expected_new = 当前作品数 - 0 = 254`，
   13 个新号一次灌进 **296 条**待报（含 2021 年的视频），下轮会全部误报成新作品。
   → 插入条件必须是 `if baselined and expected_new > 0 and pending_cnt < expected_new`。
   连带要求：**任何写入快照的地方，`aweme_count` 未知时写 `NULL` 而不是 `0`**
   （`prev_aweme is not None` 会把 NULL 挡掉，0 不会）。

12. **搜索卡片的「粉丝/获赞」是「数值在前、标签在后」（2026-09-05 修，跨 douyin-comment-analyzer）**
   卡片真实文本是 `抖音号: <id><获赞数>获赞<粉丝数>粉丝`，
   旧解析按「标签在前」取值，把两数**整体互换**。
   症状：巡查时这些账号的粉丝变化量出现巨额负数（如 -21.2万），而获赞正数等额。
   连带坑：拓号入库门槛 `followers >= min_fans`（Mark 定的"粉丝≥1000"口径）
   **一直卡的是获赞数，不是粉丝数**，等于门槛失效。
   → 正确写法见 `douyin-comment-analyzer/scripts/discover_accounts.py::parse_card_text`。
   **⚠️ 同函数第二个坑（2026-09-14 修）：粉丝解析曾被挂在「获赞带单位」的前置条件里。**
   卡片获赞 <1万 时显示**裸数**（无 万/亿），旧代码 `if re.search(rf'{UNIT}$', m.group(1)):`
   把 `likes` 和 `fans` 一起赋值 → 获赞无单位时**粉丝被一并清零**。
   后果：出海服务号多为中小号、获赞常 <1万，于是「粉丝 ≥1000」门槛对这类号**完全失效**，
   长期被静默漏掉（每日只有获赞 ≥1万 的少数号能达线，即 0-25 个）。
   实证（09-12~09-14 三日完全一致）：候选中有粉丝值的 **100% 获赞 ≥1万**；无粉丝值占绝大多数，
   且服务属性候选几乎全为 0 —— 09-14 首轮因此误报「达线 0 个」。
   → 修法：`fans = parse_count(m.group(2))` 独立解析（group(2) 位于「获赞…粉丝」之间，语义唯一，
   裸数也是合法粉丝数）；`likes` 仍保留单位校验（裸数可能是抖音号尾数）。
   回归用例：`抖音号: wang123 8342获赞 9624粉丝` → followers=9624 / likes=0（修复前 followers=0）。

13. **查库判定「真新作品」时，不能只靠 `notified=0`（2026-09-05 补充）**
   队列里可能同时混着三类：① 真新作品、② 上轮遗留待放行、③ 基线补录脏行。
   最稳的判据是**发布时间**：`monitor.py detail <aweme_id>` 拿权威 `publish_time`，
   与本轮巡查开始时间比对。aweme_id 反推时间戳**跨账号误差可达 10+ 小时，不可用**。

14. **新作品配额必须按真实插入行数计数，不能无条件自增（2026-09-06 修）**
   `cmd_run` 的判新循环里，`pending_cnt += 1` 原本紧跟 `INSERT OR IGNORE` 之后无条件执行。
   但 `aweme_id` 是 PRIMARY KEY，当该 ID 已存在（被同轮前一个账号先插走，或挂在别的
   `sec_uid` 下）时，**插入被静默忽略，名额却照烧**。
   后果：本账号真正的那条新作品排到后面时，`pending_cnt >= expected_new` 已成立，
   只能掉进 else 分支写成 `seen_count=2, notified=1`，
   **被当成基线老视频永久压制，永不报警**。
   实测：非洲大小姐 2026-09-06，作品数 487→488（确实涨了 1），
   但 9 条新见 ID 全部落进 `(2,1)`，新作品 `7681878064623652122`（208 赞）零报警。
   同轮其余 6 个作品数增长的账号都正常，说明是配额被烧掉的个案，不是系统性逻辑错误。
   → 正确写法：`cur = c.execute("INSERT OR IGNORE ..."); if (c.rowcount or 0) > 0: pending_cnt += 1`。

   📌 **配套巡检动作（每轮必做）**：核对「作品数增长量」与「本轮入队条数」是否相等。
   不等即说明又漏报了。查询模板：

   ```sql
   -- 本轮入队条数（应等于各账号 d_aweme 之和）
   SELECT a.nickname, COUNT(*) FROM videos v JOIN accounts a ON v.sec_uid=a.sec_uid
   WHERE v.discovered_at >= '<本轮开始时间>' AND v.seen_count=1 AND v.notified=0
   GROUP BY a.nickname;
   ```

   ⚠️ **2026-09-23 补：比对「作品数增量」的 CTE 必须加 `ok=1` 过滤，否则会假性漏报。**
   `snapshots` 里存在 `ok=0` 的空值快照（页面异常那次留下的，`aweme_count` 为 NULL），
   若 `prev` 子查询取到它，`c.aweme_count - p.aweme_count` 变成 NULL，
   该账号**直接整条从结果里消失**，看起来就像「作品数没涨 = 漏报」。
   实测本轮欧万海运的 prev 是 09-22 的 ok=0 快照 → 第一轮比对完全看不到它的 +2，
   误判为「入队 24 vs 增量 17，差 7 条」，加上 `AND s.ok=1` 后正好对上 23。
   → 正确写法（**两个 CTE 都要加**）：
   ```sql
   WITH cur AS (SELECT sec_uid, aweme_count FROM snapshots
                WHERE date(checked_at)='<本轮日>' AND ok=1),
   prev AS (SELECT s.sec_uid, s.aweme_count FROM snapshots s WHERE s.ok=1
            AND s.checked_at=(SELECT MAX(checked_at) FROM snapshots s2
                WHERE s2.sec_uid=s.sec_uid AND date(s2.checked_at)<'<本轮日>' AND s2.ok=1))
   SELECT a.nickname, p.aweme_count AS 前, c.aweme_count AS 后,
          c.aweme_count-p.aweme_count AS 增量
   FROM cur c JOIN prev p ON p.sec_uid=c.sec_uid JOIN accounts a ON a.sec_uid=c.sec_uid
   WHERE c.aweme_count-p.aweme_count != 0 ORDER BY 增量 DESC;
   ```

15. **有「首次巡查」账号时，`discovered_at` 过滤会被基线条目淹没（2026-09-07 补）**
   上面模板里的 `seen_count=1 AND notified=0` 是**必须的**，不要只写 `discovered_at >= 本轮开始`。
   实测 2026-09-07 那轮：只按 `discovered_at` 过滤得到 **456 条**，
   而作品数总增长只有 **15**。多出来的 441 条来自两个当轮首巡的新号
   （宝哥在非洲 73 条 + 泉州阿阳 141 条基线，加上其余账号滚动深度变化补录的老视频）。
   补上 `seen_count=1 AND notified=0` 后正好 15 条，与增长量吻合。
   → 判新作品的完整条件：
   `discovered_at >= 本轮开始 AND seen_count=1 AND notified=0`，
   再用「作品数总增长」对总数做一次校验（见坑 14 巡检）。

16. **新作品入队时不带 digg / collect / share / publish_time（2026-09-08 补）**
   `cmd_run` 走的是主页列表，只写 `aweme_id + title`，四个指标和发布时间全为 NULL。
   要拿到**藏赞比**和**发布时间**，必须在本轮结束后对每条新作品单独补一次
   `monitor.py detail <aweme_id>`（约 20s/条，19 条 ≈ 8m）。
   → 这是**固定动作，不要省**。省了就只能报点赞数，Mark 关心的
   「藏赞比 / 转赞比 = 真实需求信号」和「发布时间 = 新鲜度」全部缺失。

17. **倍数低 ≠ 内容差，先看新鲜度（2026-09-08 补）**
   每日 04:00 巡查时，新作品多数发布于前一天，距巡查仅 5–26 小时，**点赞远未发酵完成**。
   实测 2026-09-08 那轮 19 条全部 0.01x–1.45x，看着全线崩盘，实际只是太新。
   → 报倍数时必须标注为「发酵初期值」，不要直接和 `baseline_digg` 中位数横比下结论。
   真正要看的是**藏赞比 + 评论意向密度**这两个不受发酵期影响的指标。

18. **`baseline_digg` 为 NULL 的账号会静默失效（2026-09-08 补）**
   若某账号入库时作品全无点赞数据（如「山东刘娟出海非洲」23 条全 NULL），
   中位数算不出来 → `baseline_digg IS NULL` → 该账号新作品的倍数判据直接空着，
   汇报里也看不出来是「低」还是「没算」。
   → 每轮顺手跑一次巡检，发现就 `backfill` 补：
   ```sql
   SELECT nickname, baseline_digg FROM accounts
   WHERE baseline_digg IS NULL OR baseline_digg = 0;
   ```

19. **详情页抓文案会抓到 UI 按钮词，COALESCE 挡不住（2026-09-10 补）**
   `extract_video_detail` 往前找文案时，抓失败会返回「抢首评 / 喜欢 / 点击按住可拖动视频」这类
   **非空但错误**的值。`cmd_detail` 写库用的是 `title=COALESCE(NULLIF(?,''), title)`，
   只挡空字符串，**挡不住抓错的非空值**，于是主页同步来的真文案被覆盖，汇报里出现一排「抢首评」。
   2026-09-10 那轮 18 条补抓里有 6 条中招（邹先华、非洲达哥×3、胡娟、非洲信盟物流）。
   → 修复：`extract_video_detail` 内新增 `UI_TEXTS` 黑名单，`lines[j] not in UI_TEXTS` 才认作文案。
   → 若历史数据已被覆盖，真文案只能从本轮 `discovered_at` 首查结果里抢救（补抓前先查一次留底）。
   **补抓前务必先 SELECT 一遍 title 存快照**，否则真文案永久丢失。
   → **2026-09-13 新样本**：视频播放器提示语「3s 后循环播放当前视频」也会被当文案抓走
     （狮王 `7684678941482925001` 中招，真文案是无标题视频的默认占位格式
     「狮王（丽总闯非洲）于20211009发布的作品」）。
     UI_TEXTS 是穷举式黑名单，对「Ns 后循环播放」这类带变量的提示语会漏。
     **已加正则兜底**：`not re.match(r'^\d+s\s*后循环播放当前视频$', lines[j])`。
     今后遇到同类「带变量的 UI 提示语」优先加正则，不要只往黑名单里塞常量。

20. **详情补抓可能滑到「另一条视频」，把别人的文案写进本条（2026-09-11 补）**
   与坑 19 不同：坑 19 抓的是 UI 按钮词，本坑抓到的是**一条真实但完全无关的文案**——
   说明 `cmd_detail` 打开页面后 DOM 滑到了推荐流里的相邻视频。
   2026-09-11 那轮邹先华 `7683844376312794408` 中招：主页同步的真文案
   「头脑灵活但身体懒惰，你的特点配得上你的苦难！#邹先华」（806 赞）被覆盖成
   「你能不能离开修脚啊！离开修脚还可以学做防水啊」。同一次抓取 digg 返回 None，
   因 COALESCE 保护 806 未被抹掉，**但 title 没有同等保护**。
   → 判别信号：**同一次 detail 里 digg 为 None 且 title 与主查快照不一致** → 判为抓错页。
   → 修复方向：`cmd_detail` 写库前校验返回页的 aweme_id 与目标一致，不一致直接丢弃不写。
   → 当前缓解：靠坑 19 的「补抓前存 title 快照」兜底，抓错后 `UPDATE ... SET title=<快照值>` 还原。
   ⚠️ 结论：**title 快照现在同时是坑 19 和坑 20 的唯一保险，补抓前不存 = 真文案永久丢失。**
   → **2026-09-28 补充：同一 ID 连续重试无效，不要死磕。** 邹先华 `7689803034863451109`
     连抓两次都滑到评论区文本（「值得你学习，你是A1老师」），digg 均返回 None。
     处置顺序：① 重试 1 次即止；② 从上一轮 DB 已存值/主页同步值还原 title；
     ③ 报告中标注「详情抓取异常，指标待核实」，**不要因为 digg 来自主页就当它是可靠爆款**
     （该条 5682 赞 = 约 9x，但内容是与出海无关的怀旧蹭热点，判定为无效爆款）。

21. **老作品会混进「新作品」队列，且作品数 +1 会伪装成真增量（2026-09-12 补，第 2 次复发）**
   主页滚动加载每次返回的作品集合不固定，一条**几个月前发布、此前没进过库**的老视频
